Versioning and releasing the photography site

How the site names each build, how a release gets made, and how to prove which one is live. The footer label is already in place; this doc proposes the process around it.

  • Draft for review
  • Updated 28 Sep 2026
  • Current release v1.0.1
  • Deployables site Worker, results Worker

Recommendation

Keep git tags as the single record of a release, and make one command, npm run release, do everything a release needs. Tags already drive the footer label. What is missing is the routine around them: today a release is six commands run by hand, in an order you have to remember.

  • Semantic version tags (v1.2.0), with a meaning for this site: major for a redesign or changed URLs, minor for a new feature, patch for a fix.
  • One release command: check, tag, push, deploy both Workers labelled with the tag, smoke-test, record results.
  • A small /version.json so the smoke check can prove the live site is the release just made.
  • Deploys stay on your laptop for now. Deploying from GitHub on a tag push is a later, optional step.

Anatomy of a build label

The build keeps the full git describe string, even though the footer shows only part of it. Each part answers a different question.

v1.0.1-3-g8bb0581-dirty
Last release
The newest tag this commit descends from.
Commits since
How far past that release the build is.
Commit
Exactly which code, as git's short hash.
Uncommitted
Local edits: no commit holds this code.
v1.0.1Footer, for a build made exactly at a tagged commit with nothing uncommitted. This is a release.
8bb0581Footer, for any other commit. The page's markup keeps the full hash and build time.
8bb0581-dirtyFooter, for a build with local edits. Never shown as a release, so a test deploy can't pass for one.

Why not calendar or automated versions

A calendar version is a fair choice for a site that deploys daily. But it can't say whether a deploy was a typo fix or a redesign, and two releases on one day need a suffix. Fully automated tools (semantic-release, Changesets) read commit messages written in a strict format, such as feat: and fix:. That is a new habit this repository doesn't have, and a lot of machinery for one author. Semver tags keep the meaning while costing one word per release: patch, minor or major.

What the version numbers mean here

Semver was written for libraries, where "breaking" means breaking someone's code. For a website, what a visitor or search engine would notice is a better guide.

BumpWhenFrom this project
Major · 2.0.0A redesign, or anything that changes or removes URLs people may have savedRenaming a category slug; a new site layout
Minor · 1.1.0A new feature or page a visitor or the admin can use"Oldest first" sorting; the Pics Viewer details column
Patch · 1.0.1A fix, copy change or internal change with no new featureThe scroll-reveal contrast fix; the footer email removal

Adding or re-titling photos is not a release. Photos and their entries live in R2 and reach the site without a build, so they never change the version.

The release command

One command, npm run release -- patch (or minor, major), in this order. It stops at the first failure, before anything is tagged or deployed.

  1. Preflight

    On main, nothing uncommitted, level with GitHub. Otherwise it stops and says which.

  2. Check

    npm run lint, astro check, npm test, npm run test:browser. The same set you ran by hand for v1.0.0.

  3. Tag

    Works out the next version from the last tag (v1.0.1 + patch = v1.0.2) and makes an annotated tag, with the commit subjects since the last tag as its message.

  4. Record

    npm run test:record, so the results in R2 carry the release's commit.

  5. Push

    The commit and the tag to GitHub.

  6. Deploy the siteCloudflare

    wrangler deploy --tag v1.0.2 --message "…", so Cloudflare's own version list names the release too.

  7. Deploy the results Workeronly if changed

    Skipped when nothing under workers/results-api/ or the shared EXIF code changed since the last tag.

  8. Prove it

    The smoke check reads /version.json and fails unless it says v1.0.2 (see the next section).

  9. Publish notesGitHub

    gh release create v1.0.2 --generate-notes: a GitHub Release listing what changed.

What it replaces

# today, by hand, in the right order
npm test && npm run test:browser && npx astro check && npm run lint
git commit … && git tag -a v1.0.2 -m v1.0.2
npm run test:record
git push origin main && git push origin v1.0.2
npm run deploy && npm run results-api:deploy

# proposed
npm run release -- patch

Proving what is live

The footer shows the version to people. Tools need something they can read without parsing a page. Two small additions close the gap between "the deploy command succeeded" and "the site is serving that release."

/version.json

A tiny endpoint answering with what the footer already knows:

{ "label": "v1.0.2", "version": "v1.0.2", "commit": "8bb0581…", "builtAt": "2026-09-28T15:23:10Z" }

It exposes nothing new: the footer and the page markup already show all of it. It must not be cached, so a stale copy can't pass the check.

A smoke check that knows the release

npm run smoke -- --expect v1.0.2 adds one check: the live /version.json label matches. The release command passes the tag it just made. The scheduled "Live smoke check" on GitHub can keep running without it.

Rolling back

Because every deploy carries its tag into Cloudflare, going back to the previous release is one command, with no rebuild:

npx wrangler versions list          # each version shows its tag, e.g. v1.0.1
npx wrangler rollback <version-id>  # serve that version again

A rollback changes the code only. Photos and entries in R2 are untouched, which is what you want. The footer then shows the older tag, so the rollback is visible at a glance.

Open questions

Deploy from the laptop, or from GitHub?

From the laptop keeps secrets off GitHub and matches how you work today. From GitHub means every release is built from a clean checkout of a pushed tag, so a -dirty build can never ship. Suggested: laptop now, revisit after Phase 3.

Keep the "-dirty" marker in the footer?

It only appears on local builds and on a deploy made with uncommitted changes. That second case is the one worth seeing. Suggested: keep it, and have the release command refuse to run when the tree is dirty.

One version for both Workers, or one each?

The results Worker changes rarely and only matters to the Admin page. Suggested: one version for the repository. The release deploys the results Worker only when its code changed, labelled with the same tag.

Should release notes be public?

GitHub Releases are as visible as the repository itself. Suggested: yes if the repository is public, since the notes list only commit subjects. A CHANGELOG.md isn't needed on top.
